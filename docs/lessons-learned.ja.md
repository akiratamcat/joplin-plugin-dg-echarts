## 1. Joplin のプラグイン全般

### 1.1 エクスポート：ビューアスクリプトで描く図は出ない

- **何が起きたか**: 試作の1回目（ビューアスクリプトがエンジンを `import()` で読んで描く方式。基準プラグインと同じ）では、PDF のエクスポートで図が出なかった（2026-11-23。`docs/spike-results.ja.md` の 13.1節）。
- **原因**: Joplin はエクスポートのときに、プラグインのアセット（JS と CSS）をファイルとして参照せず、HTML の中に直接書き込む。ビューアスクリプトは、自分の URL（`document.currentScript.src`）からエンジンのファイルの場所を求めていたが、書き込まれたスクリプトでは URL が空になり、エンジンを読めない。エンジンのファイルはアセットとして宣言していない（基準の教訓 1.3節）ので、エクスポートの出力にも入らない。
- **対応**: 図を Markdown-it のコンテンツスクリプトの中で作り、SVG を HTML に直接入れる方式に変えた（試作の2回目）。PDF と HTML のエクスポート、ノートビューア、リッチテキストエディタのすべてで図が出た。設計書 0.4 で描画の方式を書き直した（5章、7章）。
- **次のプラグインへの示唆**:
  - **エクスポートで図を出したいなら、Markdown-it の段階で図を作る。** ビューアスクリプトで描く方式は、追加のファイル（エンジン）を読む限り、エクスポートで動かない。
  - 基準プラグイン（dg-plantuml）もビューアスクリプトで描く方式なので、エクスポートで図が出ないおそれがある（確かめていない）。
  - エクスポートと印刷は、試作の早い段階で確かめる（3.1節）。

### 1.2 Markdown-it のコンテンツスクリプトは、DOM のある renderer プロセスで動く

- **何が起きたか**: 設計書 0.3 では、Markdown-it の段階で描くと「Node.js で動くので Canvas がなく、文字の幅を見積もりで計算することになり、日本語の配置がずれる」と心配していた。試作の2回目で確かめると、心配はいらなかった。
- **原因**: Joplin のデスクトップ版は、コンテンツスクリプトを Electron の renderer プロセスで、Node の `require` で読み込む（`packages/lib/services/plugins/utils/loadContentScripts.ts` の `shim.requireDynamic`）。そこには `window`、`document` があり、画面に出さない Canvas で文字の幅を測れる（12px で「日本語のラベル」が 84px）。DOMPurify も使える。
- **対応**: ECharts の描画（`renderToSVGString`）と DOMPurify の無害化を、Markdown-it のコンテンツスクリプトの中で行う。図1つ 15ms、準備 2ms だった。
- **次のプラグインへの示唆**:
  - デスクトップ版では、DOM や Canvas が要るエンジンも Markdown-it の段階で動かせる見込みがある。ただし、**描画は同期的に終わる必要がある**（Markdown-it の規則は Promise を待たない）。非同期の API しかないエンジン（読み込みや描画が Promise を返すもの）は、この方式が使えない。
  - 描画が重いと、ノートの表示全体が待たされる。キャッシュと入力の大きさの上限が大切になる。
  - モバイル版で同じように動くかは、別に確かめる必要がある。

### 1.3 Joplin が Markdown-it のプラグインに渡す options

- **何が起きたか**: 試作の2回目の診断で、Joplin が Markdown-it のプラグインに渡す options を、場面ごとに調べた。
- **分かったこと**:
  - `options.theme.appearance`（`light` / `dark`）で、Joplin のテーマの明暗が分かる。ビューアスクリプトで背景色の明るさを測る必要はない（基準の教訓 1.7節の方法の代わりになる）。
  - **エクスポート（PDF、HTML）では、暗いテーマで使っていても `appearance` は `light` になる**。白い紙に合う配色で図を描ける。
  - ノートビューアとリッチテキストエディタでは `whiteBackgroundNoteRendering` があり、エクスポートでは代わりに `plainResourceRendering` がある。エクスポートかどうかの判定に使えそうだが、`appearance` で足りた。
  - `options.settingValue(key)` で、プラグインの設定値を描画のときに読める（Joplin の API の説明にも書かれている）。
- **対応**: 有効テーマの Auto は `appearance` で決める（設計書 8.2節）。設定値は `settingValue` で読む（設計書 9章）。
- **3回目で分かったこと**（`docs/spike-results.ja.md` の 14章）:
  - `settingValue` で、隠し設定（`public: false`）も型のとおりに読める。**設定を変えると、Joplin がノートを自動で描き直す**（設計書 V-10）。
  - options には `globalSettings` もある。Joplin の設定（表示言語、本文の文字サイズなど）をここから読めれば、メインスクリプトが隠し設定に写す仕組みは要らない（設計書 V-15。中身は未確認）。メインスクリプトの `joplin.settings.onChange` はプラグイン自身の設定にしか働かないので、隠し設定に写す方法では、Joplin の設定の変更が再起動するまで反映されない。
- **次のプラグインへの示唆**: Markdown-it の段階で描くプラグインは、テーマと設定値を options から受け取れ、設定の変更で描き直す仕組みを作る必要もない。Joplin 本体の設定は、まず `options.globalSettings` で読めるかを確かめる。

### 1.5 Markdown-it のコンテンツスクリプトから、同梱したファイルを `require` で読める

- **何が起きたか**: 設計書 0.4 で、公式の UMD の圧縮版を webpack にまとめず、実行時に Node の `require` で読むと決めた（設計書 D-09、V-13）。試作の3回目で確かめると、読めた（2026-11-23。`docs/spike-results.ja.md` の 14章）。
- **分かったこと**:
  - webpack は `__dirname` を書き換えることがある。`plugin.config.json` の `webpackOverrides` に `node: { __dirname: false }` を書くと、実際のコンテンツスクリプトのフォルダー（Joplin のプラグインのキャッシュの中）が得られる。
  - `require` は webpack が自分のものに置き換えるので、`__non_webpack_require__` を使う。
  - 読み込みは 46〜99ms（初回だけ）。UMD は `module.exports` に書き出すので、グローバル変数は作られない。
  - ECharts のロケールのファイルは、`lib/i18n/langXX.js` ではなく `i18n/langXX-obj.js` を読む（2.5節）。
- **対応**: 設計書 7.5節と 15.1節に、読み込み方を書いた。
- **次のプラグインへの示唆**: 大きなエンジンを圧縮し直さずに同梱したいとき（ライセンスや、取得元と同じことを SHA-256 で示したいとき）に使える。モバイル版で同じように読めるかは別に確かめる。

### 1.4 印刷では、プラグインの Markdown-it のコンテンツスクリプトが動かない

- **何が起きたか**: 印刷（仮想プリンタで PDF に出力）では、どちらの描画の方式でも、ECharts のブロックが普通のコードブロックとして出た。Joplin 本体の Mermaid の図は出た。
- **原因**: Joplin の問題。`packages/app-desktop/gui/WindowCommandsAndDialogs/utils/usePrintToCallback.ts` で、PDF のエクスポートの呼び出しは `plugins: props.plugins` を渡すが、印刷（`printNote`）の呼び出しは渡さない。HTML を作る関数は同じなので、印刷のときだけプラグインの Markdown-it のコンテンツスクリプトが読み込まれない（Joplin のソースの 2026-11-22 の版で確認）。
- **対応**: プラグインでは直せない。README に「印刷するときは、PDF にエクスポートしてから印刷する」と書く。Joplin には issue も PR も出さないと、作者が決めた（設計書 D-13）。
- **次のプラグインへの示唆**: Markdown-it のコンテンツスクリプトを使うどのプラグインにも当てはまる。印刷で図が出ないと報告を受けたら、まずこの問題を疑う。Joplin の新しい版で直っていないかを、ときどき確かめる。

## 2. ECharts に固有の事柄

### 2.1 テーマを指定した図は、背景を塗らないと紙で読めない

- **何が起きたか**: 試作の2回目の PDF で、`theme=dark` を指定した図の文字が、白い紙の上でほとんど見えなかった。
- **原因**: 背景を常に透明（`backgroundColor: 'transparent'`）にしていた。ECharts の `dark` テーマは薄い色の文字を使う。1回目の方式では、ビューアスクリプトがページの明暗を見て、CSS で図の後ろに背景を敷いていたが、2回目の方式にはその処理がない。
- **対応**: 図の有効テーマとページの明暗（`appearance`）が違うときは、`option` の `backgroundColor` で SVG の中に背景を塗る。SVG の中に塗るので、エクスポートでも効く（設計書 8.5節）。
- **次のプラグインへの示唆**: 図の背景を CSS で敷く方法は、ビューアスクリプトがないと使えない。Markdown-it の段階で描くときは、図そのものに背景を入れる。

### 2.2 PDF から文字を取り出すと、ラベルが二重になる

- **何が起きたか**: PDF の見た目は正常だが、文字をコピーすると「120」が「112020」、「北京市」が「北北京市京市」になった（試作の2回目）。棒の上の数値、円グラフのラベル、ノードの名前に出て、題名と軸の文字には出ない。
- **原因**（試作の3回目で確認）: ECharts がラベルに付ける縁取り（`<text stroke="..." stroke-width="2" paint-order="stroke">`）。Chromium は、縁取りの文字と塗りの文字の2つを PDF に書き込む。
  - **縁取りを外すつもりで `textBorderWidth: 0` を書いても効かない。** zrender の `graphic/Text.js` が幅を `style.lineWidth || defaultLineWidth` で決めるので、0 が既定の 2 に戻る。`textBorderColor: 'transparent'`（または `'none'`）なら外れる。
  - 二重の文字の出方は道具によって違う。Adobe Acrobat のコピーは `120120`、`pdftotext` は `112200`。Vivaldi（Chromium）のコピーは、重なった同じ文字を1つにまとめることがあり、「120」は正しく、「北京市」は `北北京京市市` だった。
- **対応**: 段階1 で、ラベルの縁取りを `textBorderColor: 'transparent'` で外す処理を入れる（設計書 14章、V-11）。
- **次のプラグインへの示唆**:
  - SVG の文字が PDF の中で正しく取り出せるか（コピー、検索）も、エクスポートの確認の項目に入れる。**Chromium の PDF ビューアだけで確かめると、二重が隠れて見落とすことがある**。Adobe Acrobat か `pdftotext` でも確かめる。
  - ライブラリのオプションで「0 にすれば消える」と思っても、`||` で既定値に戻る実装がある。出力の SVG を見て確かめる。

### 2.3 Dark のテーマの補助線が、透明の背景では見えない

- **何が起きたか**: 試作の3回目で、Joplin の暗いテーマで見ると、Dark の図の補助線（`splitLine`）がほとんど見えなかった。`theme=dark` の図を `#181818` の背景で描いた PDF でも同じ。
- **原因**: ECharts の `dark` テーマの補助線は `rgb(40, 44, 52)` で、既定の背景 `rgb(4, 8, 16)`（ほぼ黒）に合わせた色。背景を透明（Joplin の暗い背景が透ける）や `#181818` にすると、明るさの差がほとんどなくなる。
- **対応**: Dark の図では、補助線の色をプラグインで明るい色に上書きする。色は作者が見本で決める（設計書 8.5節、V-02）。
- **次のプラグインへの示唆**: ライブラリの暗いテーマの色は、ライブラリの既定の背景に合わせてある。背景を変えるときは、文字だけでなく、補助線や枠のような細くて暗い要素も見えるかを確かめる。

### 2.4 力学モデルのグラフが小さいのは ECharts の仕様

- **何が起きたか**: 試作の2回目の PDF で、力学モデルのグラフ（`layout: 'force'`）が中央に小さく固まって描かれた。
- **原因**（試作の3回目で確認）: 辺の長さの既定値が `force.edgeLength: 30`（`chart/graph/GraphSeries.js`）で、図の大きさに関係なく小さく描かれる。ノートビューアでも同じ。`edgeLength: 120` にすると約3倍になった。
- **対応**: プラグインでは変えない（利用者の `option` の意味を変えないため）。README で `force.edgeLength` と `force.repulsion` を案内する（設計書 V-12）。
- **次のプラグインへの示唆**: 図の見た目がおかしいときは、まずライブラリの既定値を調べる。プラグインの問題と決めつけない。

### 2.5 ECharts のロケールのファイルは `i18n/langXX-obj.js` を使う

- **何が起きたか**: 設計書 0.4 では、`lib/i18n/langXX.js` を同梱して登録するとしていた。試作の3回目の前に Node で確かめると、このファイルは ES モジュール（`export default`。`echarts` のパッケージは `"type": "module"`）なので、`require` で読めなかった。`i18n/langXX.js`（UMD）は `require('echarts/lib/echarts')` で本体を読みにいくので、圧縮版だけを同梱する形では使えない。
- **対応**: `i18n/langXX-obj.js`（UMD の形で、ロケールのオブジェクトだけを書き出し、本体を読まない）を `require` で読み、`registerLocale` する。試作の3回目で、日本語の月の名前になった（設計書 7.5節、10.3節）。
- **次のプラグインへの示唆**: npm のパッケージには、同じ中身のファイルが形を変えて複数入っていることがある（ES モジュール、本体を読みにいく UMD、単独で読める UMD）。同梱する形と読み込み方に合うファイルを選び、Node で読めるかを先に確かめる。

## 3. 進め方で役に立ったこと

### 3.1 エクスポートと印刷を、段階1 の前に試作で確かめた

- 設計書 0.3 の V-08 を、段階1 の最初ではなく、試作のプラグインで先に確かめた。描画の方式を変える必要が分かったので、本番のコードを書く前に設計を直せた。
- 失敗の原因（エクスポートのアセットの扱い、印刷の引数）は、Joplin のソースを読んで特定した。手元に Joplin のソースがあると、プラグインで直せる問題か、Joplin の問題かを早く切り分けられる。
- 診断のパネルに、Joplin が渡す options の項目名を出しておいたので、場面ごとの違い（`whiteBackgroundNoteRendering` と `plainResourceRendering`）がすぐに分かった。
