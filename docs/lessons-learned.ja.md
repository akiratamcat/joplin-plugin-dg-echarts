## 1. Joplin のプラグイン全般

### 1.1 エクスポート：ビューアスクリプトで描く図は出ない

- **何が起きたか**: 試作の1回目（ビューアスクリプトがエンジンを `import()` で読んで描く方式。基準プラグインと同じ）では、PDF のエクスポートで図が出なかった（2026-11-23。`docs/spike-results.ja.md` の 13.1節）。
- **原因**: Joplin はエクスポートのときに、プラグインのアセット（JS と CSS）をファイルとして参照せず、HTML の中に直接書き込む。ビューアスクリプトは、自分の URL（`document.currentScript.src`）からエンジンのファイルの場所を求めていたが、書き込まれたスクリプトでは URL が空になり、エンジンを読めない。エンジンのファイルはアセットとして宣言していない（基準の教訓 1.3節）ので、エクスポートの出力にも入らない。
- **対応**: 図を Markdown-it のコンテンツスクリプトの中で作り、SVG を HTML に直接入れる方式に変えた（試作の2回目）。PDF と HTML のエクスポート、ノートビューア、リッチテキストエディタのすべてで図が出た。設計書 0.4 で描画の方式を書き直した（5章、7章）。
- **次のプラグインへの示唆**:
  - **エクスポートで図を出したいなら、Markdown-it の段階で図を作る。** ビューアスクリプトで描く方式は、追加のファイル（エンジン）を読む限り、エクスポートで動かない。
  - 基準プラグイン（dg-plantuml）もビューアスクリプトで描く方式なので、エクスポートで図が出ないおそれがある（確かめていない）。
  - エクスポートと印刷は、試作の早い段階で確かめる（3.1節）。

### 1.2 Markdown-it のコンテンツスクリプトは、DOM のある renderer プロセスで動く

- **何が起きたか**: 設計書 0.3 では、Markdown-it の段階で描くと「Node.js で動くので Canvas がなく、文字の幅を見積もりで計算することになり、日本語の配置がずれる」と心配していた。試作の2回目で確かめると、心配はいらなかった。
- **原因**: Joplin のデスクトップ版は、コンテンツスクリプトを Electron の renderer プロセスで、Node の `require` で読み込む（`packages/lib/services/plugins/utils/loadContentScripts.ts` の `shim.requireDynamic`）。そこには `window`、`document` があり、画面に出さない Canvas で文字の幅を測れる（12px で「日本語のラベル」が 84px）。DOMPurify も使える。
- **対応**: ECharts の描画（`renderToSVGString`）と DOMPurify の無害化を、Markdown-it のコンテンツスクリプトの中で行う。図1つ 15ms、準備 2ms だった。
- **次のプラグインへの示唆**:
  - デスクトップ版では、DOM や Canvas が要るエンジンも Markdown-it の段階で動かせる見込みがある。ただし、**描画は同期的に終わる必要がある**（Markdown-it の規則は Promise を待たない）。非同期の API しかないエンジン（読み込みや描画が Promise を返すもの）は、この方式が使えない。
  - 描画が重いと、ノートの表示全体が待たされる。キャッシュと入力の大きさの上限が大切になる。
  - モバイル版で同じように動くかは、別に確かめる必要がある。

### 1.3 Joplin が Markdown-it のプラグインに渡す options

- **何が起きたか**: 試作の2回目の診断で、Joplin が Markdown-it のプラグインに渡す options を、場面ごとに調べた。
- **分かったこと**:
  - `options.theme.appearance`（`light` / `dark`）で、Joplin のテーマの明暗が分かる。ビューアスクリプトで背景色の明るさを測る必要はない（基準の教訓 1.7節の方法の代わりになる）。
  - **エクスポート（PDF、HTML）では、暗いテーマで使っていても `appearance` は `light` になる**。白い紙に合う配色で図を描ける。
  - ノートビューアとリッチテキストエディタでは `whiteBackgroundNoteRendering` があり、エクスポートでは代わりに `plainResourceRendering` がある。エクスポートかどうかの判定に使えそうだが、`appearance` で足りた。
  - `options.settingValue(key)` で、プラグインの設定値を描画のときに読める（Joplin の API の説明にも書かれている）。
- **対応**: 有効テーマの Auto は `appearance` で決める（設計書 8.2節）。設定値は `settingValue` で読む（設計書 9章）。
- **3回目で分かったこと**（`docs/spike-results.ja.md` の 14章）:
  - `settingValue` で、隠し設定（`public: false`）も型のとおりに読める。**設定を変えると、Joplin がノートを自動で描き直す**（設計書 V-10）。
  - options には `globalSettings` もある。Joplin の設定（表示言語、本文の文字サイズなど）をここから読めれば、メインスクリプトが隠し設定に写す仕組みは要らない（設計書 V-15。中身は未確認）。メインスクリプトの `joplin.settings.onChange` はプラグイン自身の設定にしか働かないので、隠し設定に写す方法では、Joplin の設定の変更が再起動するまで反映されない。
- **次のプラグインへの示唆**: Markdown-it の段階で描くプラグインは、テーマと設定値を options から受け取れ、設定の変更で描き直す仕組みを作る必要もない。Joplin 本体の設定は、まず `options.globalSettings` で読めるかを確かめる。

### 1.4 印刷では、プラグインの Markdown-it のコンテンツスクリプトが動かない

- **何が起きたか**: 印刷（仮想プリンタで PDF に出力）では、どちらの描画の方式でも、ECharts のブロックが普通のコードブロックとして出た。Joplin 本体の Mermaid の図は出た。
- **原因**: Joplin の問題。`packages/app-desktop/gui/WindowCommandsAndDialogs/utils/usePrintToCallback.ts` で、PDF のエクスポートの呼び出しは `plugins: props.plugins` を渡すが、印刷（`printNote`）の呼び出しは渡さない。HTML を作る関数は同じなので、印刷のときだけプラグインの Markdown-it のコンテンツスクリプトが読み込まれない（Joplin のソースの 2026-11-22 の版で確認）。
- **対応**: プラグインでは直せない。README に「印刷するときは、PDF にエクスポートしてから印刷する」と書く。Joplin には issue も PR も出さないと、作者が決めた（設計書 D-13）。
- **次のプラグインへの示唆**: Markdown-it のコンテンツスクリプトを使うどのプラグインにも当てはまる。印刷で図が出ないと報告を受けたら、まずこの問題を疑う。Joplin の新しい版で直っていないかを、ときどき確かめる。

### 1.5 Markdown-it のコンテンツスクリプトから、同梱したファイルを `require` で読める

- **何が起きたか**: 設計書 0.4 で、公式の UMD の圧縮版を webpack にまとめず、実行時に Node の `require` で読むと決めた（設計書 D-09、V-13）。試作の3回目で確かめると、読めた（2026-11-23。`docs/spike-results.ja.md` の 14章）。
- **分かったこと**:
  - webpack は `__dirname` を書き換えることがある。`plugin.config.json` の `webpackOverrides` に `node: { __dirname: false }` を書くと、実際のコンテンツスクリプトのフォルダー（Joplin のプラグインのキャッシュの中）が得られる。
  - `require` は webpack が自分のものに置き換えるので、`__non_webpack_require__` を使う。
  - 読み込みは 46〜99ms（初回だけ）。UMD は `module.exports` に書き出すので、グローバル変数は作られない。
  - ECharts のロケールのファイルは、`lib/i18n/langXX.js` ではなく `i18n/langXX-obj.js` を読む（2.5節）。
- **対応**: 設計書 7.5節と 15.1節に、読み込み方を書いた。
- **次のプラグインへの示唆**: 大きなエンジンを圧縮し直さずに同梱したいとき（ライセンスや、取得元と同じことを SHA-256 で示したいとき）に使える。モバイル版で同じように読めるかは別に確かめる。

### 1.6 デスクトップ版のノートの文字サイズは、テーマの `noteViewerFontSize`

- **何が起きたか**: 設計書では、設定「図の文字サイズをノートの本文に合わせる」のために、Joplin の設定 `style.viewer.fontSize` をメインスクリプトが読んで隠し設定に写すとしていた（段階1 で実装）。段階2 で Joplin のソースを確かめると、この設定はモバイル版だけのもの（`appTypes: [AppType.Mobile]`）で、デスクトップ版のノートの本文の大きさとは関係がなかった（2026-11-24。`docs/design.ja.md` の 8.7節、9章）。
- **原因**: デスクトップ版のノートビューアの本文は、テーマの `noteViewerFontSize`（12 × 1.25 = 15px の固定）で描かれる（Joplin の `packages/renderer/noteStyle.ts`、`packages/lib/theme.ts`）。デスクトップ版の「エディタの文字サイズ」（`style.editor.fontSize`）はエディタにしか効かない。画面全体のズームは、本文と図に同じように効く。
- **対応**: Joplin が Markdown-it のプラグインに渡す `options.theme.noteViewerFontSize` を読むようにし、本文の文字サイズの隠し設定と、ノートを選び直したときに写し直す処理をやめた。`MdToHtml` は options をそのまま規則に渡すので、テーマの値はプラグインからも読める。
- **次のプラグインへの示唆**:
  - Joplin の設定を使うときは、`builtInMetadata.ts` の `appTypes` を見て、デスクトップ版の設定かを確かめる。名前（`style.viewer.*`）だけで決めない。
  - Markdown-it のプラグインでは、本文の大きさや色は `options.theme` から読める。メインスクリプトから写す必要はない。
  - `options.globalSettings` には ABC 記法の設定（`markdown.plugin.abc.options`）しか入らない（V-15）。Joplin の表示言語は、今のところ隠し設定に写すしかない（表示言語の変更は Joplin の再起動を伴うので、起動時に写せば足りる）。

### 1.7 ビューアスクリプトは、Markdown-it のプラグインが付けた属性を読めば、設定を問い合わせなくてよい

- **何が起きたか**: 段階4 でツールバー（コピー、保存）を作るとき、基準プラグインはビューアスクリプトがメインスクリプトに設定と翻訳を問い合わせていた（`getConfig`）。dg-echarts では、図そのものは Markdown-it の段階で描くので、ビューアスクリプトは「ツールバーを付けるか」と「何語で付けるか」だけを知ればよかった。
- **対応**: Markdown-it のプラグインが、図の要素に `data-echarts-toolbar`（設定が有効で、図が描けたとき）と `data-echarts-lang`（表示の言語）を付け、ビューアスクリプトはそれを読み、翻訳の表を自分で持つ。メインスクリプトとのやり取りは、コピーと保存の依頼だけになった。メインスクリプトのないページ（HTML のエクスポート。`window.webviewApi` がない）では、押しても何もできないボタンを付けないようにした。
- **次のプラグインへの示唆**: Markdown-it の段階で HTML を作るプラグインは、ビューアに渡したい値を HTML の属性に入れられる。設定を変えると Joplin がノートを描き直すので、属性もいつも最新になる（1.3節）。

### 1.8 リッチテキストエディタから Markdown に戻すと、本文の記号がエスケープされる

- **何が起きたか**: 段階1 の手動テストで、リッチテキストエディタでグラフを編集してから Markdown エディタに戻すと、本文の `[chart]` が `\[chart\]` に、見出しの `1.` が `1\.` になった（2026-11-24）。
- **原因**: Joplin がリッチテキストエディタの内容を Markdown に戻すときの変換の動き。プラグインは関係しない。` ```echarts ` のブロックの中は変わらない。
- **対応**: 設計書の進み具合に記録しただけ（直すものはない）。手動テスト用のノートの見出しに `[chart]` のような印を使うと、この変換が目立つ。
- **次のプラグインへの示唆**: リッチテキストエディタとの往復のテストでは、ブロックの中が変わらないことを確かめる。ブロックの外の本文の変化は Joplin の動きなので、不具合と取り違えない。

### 1.9 新しい V8 の JSON のエラーには、位置が入らないことがある（1.0.1 で修正）

- **何が起きたか**: 作者の Vega-Lite のプラグインの段階1 の描画テストで、JSON の構文の誤り（`[1, 2,]`）の行番号が出なかった（dg-vega-lite の教訓 1.1節）。同じ処理（`input.ts` の `jsonErrorLine`）を使う本プラグインでも、Node 24 で同じことを確かめた（2026-11-25）。描画テストの JSON の誤りの例（テストノートの15番）は、位置の入る種類の誤りだったので、気づかなかった。
- **原因**: Node 20 以降と Chrome の V8 は、一部の誤り（`Unexpected token`）で、位置の代わりに前後の文字を引用する（`Unexpected token ']', "..." is not valid JSON`）。引用は、誤りの位置の前の最大 10 文字（切ったときは `...`）と後の 10 文字。ほかの誤りには、今も位置が入る。
- **対応**: 引用された文字をソースの中で探して位置を求める処理を、dg-vega-lite から移した（`input.ts`。単体テストに、実際の `JSON.parse` のメッセージで4つの形を加えた）。
- **次のプラグインへの示唆**: エンジンや実行環境のエラーの文の形は、版で変わる。テストには、決め打ちのメッセージだけでなく、今の実行環境で実際に出したメッセージを使う。誤りの例は、メッセージの形ごとに1つずつ用意する。

## 2. ECharts に固有の事柄

### 2.1 テーマを指定した図は、背景を塗らないと紙で読めない

- **何が起きたか**: 試作の2回目の PDF で、`theme=dark` を指定した図の文字が、白い紙の上でほとんど見えなかった。
- **原因**: 背景を常に透明（`backgroundColor: 'transparent'`）にしていた。ECharts の `dark` テーマは薄い色の文字を使う。1回目の方式では、ビューアスクリプトがページの明暗を見て、CSS で図の後ろに背景を敷いていたが、2回目の方式にはその処理がない。
- **対応**: 図の有効テーマとページの明暗（`appearance`）が違うときは、`option` の `backgroundColor` で SVG の中に背景を塗る。SVG の中に塗るので、エクスポートでも効く（設計書 8.5節）。
- **次のプラグインへの示唆**: 図の背景を CSS で敷く方法は、ビューアスクリプトがないと使えない。Markdown-it の段階で描くときは、図そのものに背景を入れる。

### 2.2 PDF から文字を取り出すと、ラベルが二重になる

- **何が起きたか**: PDF の見た目は正常だが、文字をコピーすると「120」が「112020」、「北京市」が「北北京市京市」になった（試作の2回目）。棒の上の数値、円グラフのラベル、ノードの名前に出て、題名と軸の文字には出ない。
- **原因**（試作の3回目で確認）: ECharts がラベルに付ける縁取り（`<text stroke="..." stroke-width="2" paint-order="stroke">`）。Chromium は、縁取りの文字と塗りの文字の2つを PDF に書き込む。
  - **縁取りを外すつもりで `textBorderWidth: 0` を書いても効かない。** zrender の `graphic/Text.js` が幅を `style.lineWidth || defaultLineWidth` で決めるので、0 が既定の 2 に戻る。`textBorderColor: 'transparent'`（または `'none'`）なら外れる。
  - 二重の文字の出方は道具によって違う。Adobe Acrobat のコピーは `120120`、`pdftotext` は `112200`。Vivaldi（Chromium）のコピーは、重なった同じ文字を1つにまとめることがあり、「120」は正しく、「北京市」は `北北京京市市` だった。
- **対応**: 段階1 で、ラベルの縁取りを `textBorderColor: 'transparent'` で外す処理を入れる（設計書 14章、V-11）。
- **次のプラグインへの示唆**:
  - SVG の文字が PDF の中で正しく取り出せるか（コピー、検索）も、エクスポートの確認の項目に入れる。**Chromium の PDF ビューアだけで確かめると、二重が隠れて見落とすことがある**。Adobe Acrobat か `pdftotext` でも確かめる。
  - ライブラリのオプションで「0 にすれば消える」と思っても、`||` で既定値に戻る実装がある。出力の SVG を見て確かめる。

### 2.3 Dark のテーマの補助線が、透明の背景では見えない

- **何が起きたか**: 試作の3回目で、Joplin の暗いテーマで見ると、Dark の図の補助線（`splitLine`）がほとんど見えなかった。`theme=dark` の図を `#181818` の背景で描いた PDF でも同じ。
- **原因**: ECharts の `dark` テーマの補助線は `rgb(40, 44, 52)` で、既定の背景 `rgb(4, 8, 16)`（ほぼ黒）に合わせた色。背景を透明（Joplin の暗い背景が透ける）や `#181818` にすると、明るさの差がほとんどなくなる。
- **対応**: Dark の図では、補助線の色をプラグインで明るい色に上書きする。色は作者が見本で決める（設計書 8.5節、V-02）。
- **次のプラグインへの示唆**: ライブラリの暗いテーマの色は、ライブラリの既定の背景に合わせてある。背景を変えるときは、文字だけでなく、補助線や枠のような細くて暗い要素も見えるかを確かめる。

### 2.4 力学モデルのグラフが小さいのは ECharts の仕様

- **何が起きたか**: 試作の2回目の PDF で、力学モデルのグラフ（`layout: 'force'`）が中央に小さく固まって描かれた。
- **原因**（試作の3回目で確認）: 辺の長さの既定値が `force.edgeLength: 30`（`chart/graph/GraphSeries.js`）で、図の大きさに関係なく小さく描かれる。ノートビューアでも同じ。`edgeLength: 120` にすると約3倍になった。
- **対応**: プラグインでは変えない（利用者の `option` の意味を変えないため）。README で `force.edgeLength` と `force.repulsion` を案内する（設計書 V-12）。
- **次のプラグインへの示唆**: 図の見た目がおかしいときは、まずライブラリの既定値を調べる。プラグインの問題と決めつけない。

### 2.5 ECharts のロケールのファイルは `i18n/langXX-obj.js` を使う

- **何が起きたか**: 設計書 0.4 では、`lib/i18n/langXX.js` を同梱して登録するとしていた。試作の3回目の前に Node で確かめると、このファイルは ES モジュール（`export default`。`echarts` のパッケージは `"type": "module"`）なので、`require` で読めなかった。`i18n/langXX.js`（UMD）は `require('echarts/lib/echarts')` で本体を読みにいくので、圧縮版だけを同梱する形では使えない。
- **対応**: `i18n/langXX-obj.js`（UMD の形で、ロケールのオブジェクトだけを書き出し、本体を読まない）を `require` で読み、`registerLocale` する。試作の3回目で、日本語の月の名前になった（設計書 7.5節、10.3節）。
- **次のプラグインへの示唆**: npm のパッケージには、同じ中身のファイルが形を変えて複数入っていることがある（ES モジュール、本体を読みにいく UMD、単独で読める UMD）。同梱する形と読み込み方に合うファイルを選び、Node で読めるかを先に確かめる。

### 2.6 `textStyle.fontSize` が効く文字は限られる

- **何が起きたか**: 設計書では、基本の文字サイズを `textStyle.fontSize` に入れれば、図の文字が大きくなると考えていた（V-01）。段階2 で確かめると、軸の目盛りの文字などは 12px のままだった（2026-11-24）。
- **原因**: `textStyle.fontSize` が効くのは、系列のラベル、凡例、軸の名前、円グラフのラベル、レーダーの項目名だけ。軸の目盛りの文字（12px）、題名（18px）、副題（12px）、ゲージの目盛り・名前・値（12、16、30px）、サンキー図のノード名（12px）、テーマリバーのラベル（11px）は、テーマの中の自分の既定の大きさを使う。
- **対応**: これらの場所に、既定の大きさを基本の文字サイズとの比率で大きくした値を入れる（利用者が書いていなければ。`src/contentScript/fontSize.ts`）。最小の文字サイズは、`option` の中のすべての `fontSize` を引き上げたうえで、同じ場所にも値を入れる。22種類の系列と、題名・凡例・時間軸・カレンダー・極座標・マークの図で、最小を 16px にすると 16px 未満の文字が残らないことをテストで確かめた（`tests/fontSize.test.ts`）。
- **次のプラグインへの示唆**: 「全体の文字サイズ」の設定がライブラリにあっても、すべての文字に効くとは限らない。描いた SVG の `font-size` を全部集めて、効いていない文字を探す。見つかった場所は、テストで固定する。

### 2.7 カスタム系列は、関数が書けないと使えない

- **何が起きたか**: 段階1 で系列の種類ごとに描けるかを確かめると、`custom` 系列だけは描く手段がなかった。
- **原因**: `custom` 系列は、描く関数（`renderItem`）が必須。dg-echarts は入力を JSON / YAML として読み、JavaScript として評価しないので、関数を書けない。
- **対応**: 制限事項として README と設計書（6.3節）に書いた。系列の種類の一覧（`optionCheck.ts`）には残す（ECharts が知っている種類なので、「未知の種類」とは言わない）。
- **次のプラグインへの示唆**: 設定を JSON で書かせるエンジンでは、関数が必須の機能を早めに洗い出して、制限事項に書く。

### 2.8 公式の圧縮版では、系列の種類の一覧をファイルから取り出せない

- **何が起きたか**: 段階1 で、プラグインの検査（未知の系列の種類）のために、ECharts 6.1.0 の系列の種類の一覧を配布ファイルから取り出そうとした。`"series.xxx"` の文字列は一部しか見つからなかった。また、たくさんの部品（`radar`、`parallelAxis`、`singleAxis` など）を1つの `option` に入れて種類ごとに描くと、例外になった。
- **対応**: 一覧は ECharts の設定の説明から作り（23種類）、種類ごとに描ける最小の例を用意して、「一覧のすべての種類が描けること」をテストにした（`tests/helpers/samples.ts`、`tests/optionCheck.test.ts`）。エンジンを更新するときは、このテストで一覧を見直す（`vendor/echarts/SOURCE.md`）。
- **次のプラグインへの示唆**: 圧縮版から内部の一覧を取り出すのは当てにならない。資料から一覧を作り、最小の例で1つずつ確かめるテストにする。

### 2.9 ECharts の SVG の凡例は、文字が色の見本より少し下に描かれる

- **何が起きたか**: 段階2 の手動テストで、作者が「円グラフの凡例で、色の見本と文字の下端がずれていて不自然」と指摘した（2026-11-24）。
- **原因**: ECharts の SVG は、文字を `dominant-baseline="central"`（文字の枠の上下の中央）で縦の中央にそろえる。既定のフォント（Microsoft YaHei）では、この中央が見た目の中心より少し下になり、文字が 1〜2px 下に見える。日本語でも英字でも同じ。`middle` にしても、フォントを変えても、ほとんど変わらなかった。
- **対応**: すべての文字の縦位置を変えると別の所がずれるおそれがあるので、直さずに、ECharts の見た目として設計書（8.7節）に記録した。
- **次のプラグインへの示唆**: SVG を出すエンジンの見た目の細かい違いは、Chrome で描いて拡大して確かめる（Playwright で `deviceScaleFactor: 3` にして撮ると分かりやすい）。直すかどうかは、ほかの文字への影響を見て決める。

### 2.10 大きな図の描画の時間は、文字数よりも要素の数で決まる

- **何が起きたか**: 段階2 で、最大文字数の既定値（200000 文字）を決めるために、描画の時間を測った（V-14）。
- **分かったこと**:
  - 時間は文字数より図の要素の数に比例する。折れ線 2万点（7.8万文字）は 120ms、散布図 1万点（9.8万文字）は 1.4秒、円グラフ 5000切れ（14.3万文字）は 1.5秒だった（jsdom の中、無害化を含む）。
  - jsdom の中では、時間の大半が DOMPurify（無害化）だった。Joplin（Chromium）の中では速く、作者の手動テストで散布図 1万点が 547ms、円グラフ 5000切れが 800ms（書き換えたときは 1072ms）だった。
  - 変更のない図はキャッシュから出るので、小さな図を書き換えても、同じノートの大きな図のために待たされることはない。
- **対応**: 最大文字数の既定値は 200000 文字のままにした。200ms 以上かかった図は、時間を開発者ツールのコンソールに出す。大きな図のノートを作るスクリプト（`tests/manual/generate-large-note.cjs`）を残した。
- **次のプラグインへの示唆**: 描画の時間は jsdom で測ると大きく出るので、上限を決めるときは Joplin の中で測る。コンソールに時間を出す仕組みを入れておくと、作者に測ってもらいやすい。

### 2.11 jsdom の「Canvas は未実装」の知らせが、ECharts の警告として拾われる

- **何が起きたか**: 段階1 で、jsdom の中で描くテストを書くと、図の下の注意に `{"type":"not implemented"}` が並んだ。
- **原因**: ECharts は画面に出さない Canvas で文字の幅を測ろうとする。jsdom の `getContext()` は「未実装」を `console.error` に出し、プラグインは描画の間の `console.error` を ECharts の警告として集めていた。
- **対応**: テストでは、`HTMLCanvasElement.prototype.getContext` が何も言わずに `null` を返すようにした（`tests/helpers/engine.ts` の `quietCanvas`）。zrender は文字の幅を見積もりで計算する。Joplin には Canvas があるので、この問題は起きない。
- **次のプラグインへの示唆**: 描画の間の警告を集める仕組みは、テストの環境の警告も拾う。テストの環境の違いで出る警告は、テストの側で止める。

### 2.12 ECharts 6 では、題名と `legend.top: 30` の凡例が重なる

- **何が起きたか**: 段階5 で、画面キャプチャ用のノートの1つ目のグラフで、題名と凡例が重なった（2026-11-24）。最小の文字サイズを 0 にしても同じだった。
- **原因**: ECharts 6 の既定のテーマでは、題名が少し下に描かれる。ECharts 5 の例によくある `legend: { top: 30 }` では、題名と重なる。
- **対応**: 凡例をグラフの下（`legend: { bottom: 0 }`）に移した。プラグインの変更ではない。
- **次のプラグインへの示唆**: ノートの例や README の例は、エンジンの今の版で描いて目で確かめる。ほかの版の例をそのまま使わない。

### 2.13 色の値の CSS の `url()` と、強調表示の `<style>` で外部が読まれる（1.0.1 で修正）

- **何が起きたか**: v1.0.0 の公開の後、作者の Vega-Lite のプラグインの段階1 の描画テストで、背景の値に書いた `url(https://...)` で外部への要求が出た（dg-vega-lite の教訓 2.1節）。ECharts でも、`backgroundColor`、`itemStyle.color`、`borderColor`、`textStyle.color` に書いた `url(https://...)` が、そのまま SVG の `fill` と `stroke` に出た（2026-11-24）。修正の調査で、`emphasis` の色が SVG の `<style>` の `:hover` の規則にそのまま書かれ、`red;}svg{background-image:image-set("https://...")}` のような値で、ノート全体に効く任意の CSS を加えられ、`url()` を使わずに外部を読めることも分かった（2026-11-25）。試作の段階B の悪意のある入力の試験（B-7）と、描画テストの画像の各種の指定の試験では見つからなかった経路。
- **原因**: ECharts（zrender の SVG の出力）は、色の値を検査せずに属性と CSS に書く。SVG の `fill="url(...)"` と CSS の `url()`・`image-set()` は、ブラウザが外部のファイルとして読みにいく。DOMPurify の SVG のプロファイルは、属性の値の `url()` も、`<style>` の中身も検査しない。プラグインのフックは `<image>` と `<a>` の `href` しか見ていなかった。Joplin のノートビューアには CSP がなく、コンテンツスクリプトの CSP も外部の画像を止めない（設計書 4.1節）。
- **対応**: DOMPurify のフックで、SVG の中を指す `url(#…)` 以外の `url()` を含む属性を取り除く（`fill` と `stroke` は、消すと黒く塗られるので `none` にする。CSS のエスケープやコメントを含む値も外部とみなす。dg-vega-lite と同じ処理）。`<style>` は、zrender が書く形の行だけで外部の `url()` がないときだけ残し、そうでなければ中身を空にする（`sanitize.ts` の `isChartCss`。設計書 12章）。系列の種類ごとの見本（両方の配色の 38 個の図、70 個の `<style>`）で、ふつうの `<style>` がすべて残ることを確かめ、テストに入れた。描画テストに、4つの項目の `url()` と `emphasis` の色の CSS で要求が出ないことを加え、修正の前のコードでは5つの要求が記録されて失敗することを確かめた。非公開の advisory（GHSA-78wh-pm82-33cq）に記録し、1.0.1 を出してから公開する（`SECURITY.md` の方針）。
- **次のプラグインへの示唆**: 外部への読み込みの経路は、画像の要素とリンクだけではない。色やスタイルを利用者が書けるエンジンでは、属性の値の CSS の `url()` と、エンジンが出力する `<style>` の中身も調べる。禁止の文字列を探すより、エンジンが書く形だけを許す（許可リスト）ほうが、`image-set()` のような見落としに強い。描画テストで出力をページに表示して要求を記録する方法（3.2節）は、こうした見落としを見つけられる。悪意のある入力の試験には、色の値に `url()` と `;}` を入れる例を加える。

## 3. 進め方で役に立ったこと

### 3.1 エクスポートと印刷を、段階1 の前に試作で確かめた

- 設計書 0.3 の V-08 を、段階1 の最初ではなく、試作のプラグインで先に確かめた。描画の方式を変える必要が分かったので、本番のコードを書く前に設計を直せた。
- 失敗の原因（エクスポートのアセットの扱い、印刷の引数）は、Joplin のソースを読んで特定した。手元に Joplin のソースがあると、プラグインで直せる問題か、Joplin の問題かを早く切り分けられる。
- 診断のパネルに、Joplin が渡す options の項目名を出しておいたので、場面ごとの違い（`whiteBackgroundNoteRendering` と `plainResourceRendering`）がすぐに分かった。

### 3.2 描画テストは、ビルドしたコンテンツスクリプトを Node で動かし、Chrome で表示した

- 設計書 0.4 では、テスト用のページの中で Markdown-it とプラグインを動かすとしていた。ところが、dg-echarts のコンテンツスクリプトは、エンジンを Node の `require` で読む（1.5節）ので、ブラウザのページの中では動かない。
- そこで、ビルドした `dist/contentScript/markdownItPlugin.js` を Node で読み込み（DOMPurify の `window` は jsdom で用意し、エンジンは `dist/contentScript/engine/` から `require` で読む）、できた HTML を Joplin の CSP のページに入れて、ヘッドレスの Chrome で確かめる形にした（`tests/render/renderPage.ts`）。ビルドの設定（`__dirname`、エンジンのコピー）の誤りも、このテストで見つかる。
- 手動テスト用のノート（`tests/manual/mvp-note.md`）の見出しに `[chart]`、`[error]`、`[note]` の印を付け、描画テストがその印を読んで期待する結果を確かめるようにした。作者が Joplin で見るノートと、自動テストのノートが同じになり、食い違いがなくなった。
- ビューアスクリプト（ツールバー）は、偽の `webviewApi` を用意して Chrome で動かし、ボタンがメインスクリプトに送る SVG、PNG、ソースを確かめた（`tests/render/toolbar.test.ts`）。PNG への変換は Canvas が要るので、jsdom ではなく Chrome で確かめる必要がある。

### 3.3 Playwright でページに渡す関数に `async` を使わない

- **何が起きたか**: 段階4 のツールバーのテストで、ボタンを押してもメッセージが1つも届かなかった。
- **原因**: テストの TypeScript は `target: es2015` で変換されるので、`async` の関数は補助関数（`__awaiter`）を呼ぶ形になる。`page.addInitScript` や `page.evaluate` に渡した関数はページの中で動くが、ページにはその補助関数がなく、`ReferenceError: __awaiter is not defined` になっていた（偽の `webviewApi.postMessage` が `async` だったため、ビューアスクリプトの呼び出しの中で例外になっていた）。
- **対応**: ページに渡す関数では `async` を使わず、`Promise.resolve()` や `.then()` で書いた。テストのファイルに理由のコメントを書いた。
- **次のプラグインへの示唆**: Playwright でページに渡す関数は、TypeScript の変換の結果がそのままページで動く。`async`、`for...of`（古い target）などの補助関数が要る書き方を避ける。原因が分からないときは、`page.evaluate` の中で呼んだ結果を `try` で受けて、エラーの文を出してみる。

### 3.4 手動テストの記録に、PC のパスが入りやすい

- **何が起きたか**: 作者が手動テストの結果を手順書に書くとき、出力したファイルの場所や、開発者ツールのコンソールの行（`C:\Users\…\markdownItPlugin.js:2`）をそのまま貼った。段階1 の記録は、そのままコミット（`feature/mvp` の 5e02da1）に入った。基準プラグインの公開前の検査（`check:publish`）は `C:\Users\` の形しか見ていなかったので、`C:\git_repos\…` の形は見つけられなかった。
- **対応**:
  - 手順書に「PC のパスは書かずに、`spike/test/...` のように書く」と書き、記録の中のパスは Claude が相対パスに直した。
  - `check:publish` を、ドライブ名に実際のフォルダー名が2段続く形（`C:\<folder>\<folder>\`）も見つけるように広げた。文書の中の例示（後ろが `…` や `...` のもの）を拾わないように、パターンを調整した。
  - 公開するときは、`feature/mvp` を1つのコミットにまとめて `main` にマージし（squash）、`main` だけを push した。古い版の PC のパスは、手元の `feature/mvp` にだけ残る。
- **次のプラグインへの示唆**: 作者が書く記録（手順書、証跡のファイル）は、コミットの前に `check:publish` を通す。開発のブランチの履歴をそのまま公開しない形（squash のマージ）にしておくと、履歴に入った誤りを公開に持ち込まずに済む。

### 3.5 大きな出力のファイルは、全体を読まずにスクリプトで調べる

- **何が起きたか**: 試作の3回目で、Joplin の HTML のエクスポート（約 2.9MB）をチャットに添付すると、生成 AI の作業が続けられなくなった。ほとんどは Joplin 本体の Mermaid のスクリプト（約 2.7MB）だった。
- **対応**: 以後、作者はテストの出力を `spike/test/` や `tests/evidence/` に置いて場所を伝え、Claude はファイルの全体を読まず、スクリプトで必要な部分（図の SVG の属性、文字、色、縁取り、外部の URL、診断の行）だけを取り出して調べた。PDF は `pdftotext` で文字を取り出した。
- **次のプラグインへの示唆**: エクスポートの結果を確かめるときは、ファイルを置く場所を決め、調べ方（スクリプト）を用意しておく。証跡のファイルを残すときは、`.gitattributes` で改行の変換を止める（`tests/evidence/** -text`）。

### 3.6 英日併記の文書は、日本語版から生成する

- 作者の決定で、GitHub とプラグインのサイトで目立つ文書（README、CONTRIBUTING、SECURITY、CHANGELOG）は、前半を英語、後半を日本語にした。日本語は `*.ja.md` を直し、`npm run docs`（`scripts/bilingual.mjs`。基準プラグインの `readme.mjs` を複数の文書に広げたもの）で英語版の後半に写す。`npm test` の中の `docs:check` で食い違いを見つける。
- CHANGELOG.md の後半に日本語が付くと、リリースノートを作るスクリプトが最後の版の節を「次の `## [`」まで読み、日本語まで取り込んでしまう。次の `## ` の見出しで止めるように直した（`.github/scripts/release-notes.js`）。
- 説明文（`manifest.json`、`package.json`）と Issue・プルリクエストのひな形は、英語の後に「 / 」で日本語を続けた。
- **次のプラグインへの示唆**: 英日併記を、手で2か所を直す形にしない。片方から生成し、検査で食い違いを止める。生成した文書を読むほかのスクリプト（リリースノートなど）が、後半の言語を誤って読まないかも確かめる。

### 3.7 Trusted Publishing の登録がないと、npm の公開は 404 で失敗する（1.0.1）

- **何が起きたか**: 1.0.1 のタグを push したところ、リリース用のワークフローの `npm` のジョブが `E404 Not Found - PUT https://registry.npmjs.org/joplin-plugin-dg-echarts` で失敗した。GitHub Releases のリリースはできていた。
- **原因**: npmjs.com で Trusted Publishing を登録する前に、変数 `NPM_PUBLISH` を `true` にしてタグを push した。npm は、公開の権限がないときも 404 を返す。手元の端末の npm へのログインは、GitHub Actions からの公開には関係しない。また、Trusted Publishing の登録の画面の Allowed actions は、何も選ばないと `npm stage publish` しか許さない。ワークフローは `npm publish` で直接公開するので、「Allow npm publish」を選ぶ必要がある。
- **対応**: オーナーが Trusted Publishing を登録し（Allowed actions は「Allow npm publish」だけ）、`gh run rerun <実行の ID> --failed` で失敗したジョブだけをやり直して公開できた。タグは作り直さなかった。`docs/release.ja.md` の 3.1 に、Allowed actions の選び方と、404 のときの直し方を書き足した。
- **次のプラグインへの示唆**: Trusted Publishing の登録が済んだことを、タグを push する前にオーナーに画面で確かめてもらう（登録の有無は、2段階認証のため生成 AI からは確かめられない）。npm の 404 は「パッケージがない」とは限らず、権限がないことを表す。登録の接続は後から変えられないので、値を確かめてから作る。
