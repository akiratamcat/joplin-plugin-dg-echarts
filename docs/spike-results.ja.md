## 1. 結論

- **試作で使う版は `echarts` 6.1.0** とする（最新版。2026-05-19 公開で、2週間以上たっている）。6.1.0 より前の版には XSS の脆弱性がある（2.2節）ので、**6.1.0 以上が必須**。
- ライセンスは条件書 G-1〜G-3 を満たす。ただし、ECharts の `LICENSE` に、d3.js の一部を取り込んだことと、その BSD-3-Clause のライセンス文（`licenses/LICENSE-d3`）が書かれている。これも同梱する（個別事項の P-15 に反映済み）。
- 静的検査では、Worker、WASM、通信の API（`fetch`、`XMLHttpRequest`、`WebSocket`）、`import()` は見つからなかった。動的なコード生成は1か所あるが、描画では通らない。
- **ただし、入力に書いた画像の URL は、外部から読まれる**。段階B で確かめた結果、画像のパターン（`{ image, repeat }`）は SVG を作る途中でエンジンが `new Image()` で読み、シンボル（`image://`）、`graphic` の画像、凡例のアイコンは SVG の `<image href>` として出力され、挿入したときにブラウザが読む。どちらにも対応するため、エンジンに渡す前に入力から取り除き（4.1節）、出力の SVG からも外部の URL の画像を取り除く（10.3節）。
- 机上の評価での判定（採用推奨）は変わらない。必須の条件 D-3、D-4 などは段階B で確かめる。

## 3. 配布ファイルの形（個別事項の P-3、P-4 の確かめ）

### 3.1 配布ファイルの種類と大きさ

| ファイル | 形式 | 大きさ | 内容 |
| --- | --- | --- | --- |
| `dist/echarts.esm.min.mjs` | ES モジュール | 1,121,654 バイト | 全部入り |
| `dist/echarts.min.js` | UMD | 1,121,883 バイト | 全部入り |
| `dist/echarts.common.min.js` | UMD | 715,020 バイト | よく使う図だけ |
| `dist/echarts.simple.min.js` | UMD | 500,315 バイト | 最小限の図だけ |

**ES モジュールの形があるのは全部入りだけ**だった。common と simple は UMD だけで、`<script>` で読むと、グローバル変数 `echarts` を作る（条件書 A-8 の副作用）。

選べる方法は次の3つ。

| 方法 | 良い点 | 注意する点 |
| --- | --- | --- |
| (a) 全部入りの ES モジュールを `import()` で読む | 基準プラグインと同じ読み込み方（教訓 1.2節）。グローバル変数を作らない。取得元のファイルと同じであることを SHA-256 で確かめられる（教訓 1.8節） | 1.12MB |
| (b) common の UMD を `<script>` で読む | 0.72MB | グローバル変数 `echarts` を作る。ビューアの CSP で動的な `<script>` を使えるかを確かめる必要がある |
| (c) `echarts/core` から、SVG の描画と使う図の種類だけを webpack でまとめる（ECharts の公式の推奨の方法） | 最も小さい。Canvas の描画の部分を省ける | 取得元のファイルと同じかを確かめられない。どの図の種類を入れるかを決める必要がある |

**段階B は (a) で行う**。大きさと読み込みの時間（B-5）を測り、(c) にするかは 02 の工程で決める（6章の Q-2）。

### 3.2 テーマ

- `default` と `dark` のテーマは、配布ファイルの本体に入っている（`registerTheme('dark', ...)`）。追加のファイルはいらない。
- `theme/` のほかのテーマ（36個）は UMD のファイルで、グローバル変数 `echarts` か CommonJS の `require` を前提にしている。ES モジュールで読んだ ECharts には、そのままでは登録できない。使うなら、ビューアスクリプトに取り込む形に書き直す必要がある。v1.0 は `default` と `dark` だけにすることを推奨する。

### 3.3 ロケール（個別事項の P-13 の確かめ）

- 本体に入っているのは英語（`EN`）と中国語（`ZH`）だけ。ほかの言語は `registerLocale` で登録する必要がある。
- `i18n/langXX-obj.js` は UMD で、ブラウザで普通に読んでも何も登録されない。`lib/i18n/langXX.js` は ES モジュール（`export default` のオブジェクト）なので、**ビューアスクリプトのビルドで取り込んで `registerLocale` する**のがよい。1言語あたり数 KB。
- 用意されている言語は 27（AR、CS、DE、EL、EN、ES、FA、FI、FR、HU、IT、JA、KO、LV、NL、PL、PT-br、RO、RU、SI、SV、TH、TR、UK、VI、ZH、nb-NO）。韓国語はある。中国語は1種類（簡体字）だけ。
- 静的な SVG で、ロケールが表示に効くのは主に日付の軸（月や曜日の名前）。凡例の選択やツールボックスの文字は、静的な図には出ない。

## 4. 静的検査（手順 4、5）

`dist/echarts.esm.mjs`（圧縮していない ES モジュール）を検索し、見つかった箇所の前後を読んだ。圧縮版（`echarts.esm.min.mjs`、`echarts.min.js`、`echarts.common.min.js`）でも、同じ種類の箇所が同じ数だけ見つかった（common には地図の `new Function` がない）。

| 検索したもの | 件数 | 場所と判断 |
| --- | --- | --- |
| `new Function` | 1 | 地図のデータを文字列で渡し、かつ `JSON.parse` がない環境でだけ通る（`parseInput`）。描画では通らない |
| `eval`、文字列の `setTimeout` | 0 | − |
| Worker、`importScripts`、Service Worker | 0 | − |
| `WebAssembly` | 0 | − |
| `fetch(` | 1 | 座標系の情報を集める内部の変数名。通信ではない |
| `XMLHttpRequest`、`WebSocket`、`EventSource`、`sendBeacon`、`import()` | 0 | − |
| `new Image()` と `.src =` | 1 | zrender の `platformApi.loadImage`。画像の要素と画像のパターンを描くときに、入力に書いた URL を読む。段階B で確かめると、SVG を作る途中で読んだのは画像のパターンだけで（大きさを知るため）、シンボルなどは SVG に `<image href>` として出力された（10.3節）。どちらにしても、入力から取り除くことが必須 |
| `createElement('iframe')`、`window.open`、`document.write` | 各1〜6 | ツールボックスの「画像として保存」（古いブラウザの経路と、新しいタブを開く経路）と、`title.link`、treemap と sunburst のノードの `link`（クリックしたときに開く）。どれもクリックの操作が必要で、静的な SVG の文字列には出ない |
| `innerHTML =` | 13 | 描画の後始末（固定の文字列）、ツールボックスの「データの表示」（`lang` の文字列と、関数の `optionToContent` の戻り値）、HTML のツールチップ（`tooltip.formatter` の文字列）。ツールボックスとツールチップは、DOM に描く場合だけ動き、SVG の文字列を作る場合には動かないはず（段階B の B-7 で確かめる） |
| 外部の URL | 89 | すべてコメントの中の参考資料のリンク。通信に使うものはない |

### 4.1 入力から取り除く項目（個別事項の P-7、P-8 の確かめと追加）

資料とソースから、入力に URL や HTML を書ける項目を洗い出した。

| 項目 | 例 | 理由 |
| --- | --- | --- |
| `image://` で始まる文字列（すべての場所） | `series.symbol`、`markPoint.symbol`、`legend.icon`、`dataZoom.handleIcon`、`timeline` のアイコン、`visualMap` の `symbol`、`pictorialBar` の `symbol`、`decal.symbol` | 描画の途中で画像を読む（`path://` は SVG のパスなので問題ない） |
| キー `image` | `graphic` の `type: 'image'` の `style.image`、色の指定の画像のパターン `{ image, repeat }`（`backgroundColor`、`itemStyle.color`、`areaStyle.color` など）、リッチテキストの `backgroundColor: { image }` | 同上 |
| `toolbox` | − | 静的な図では使わない。「データの表示」に HTML が入る経路がある |
| `tooltip` | − | 静的な図では出ない。HTML が入る経路がある |
| `link`、`sublink`（`title`、treemap と sunburst のノード） | − | クリックで `window.open` する。静的な図では動かないが、念のため取り除く |
| 地図（`geo`、`series.type: 'map'`、`registerMap`） | − | v1.0 は対象外（地図のデータを同梱しない）。分かりやすいエラーにする |

- 取り除くのは、場所を決め打ちにせず、**入力のオブジェクト全体を走査して、上の規則に当たる値をすべて取り除く**方式を推奨する。ECharts の設定の項目は非常に多く、場所の一覧では漏れが出るため。
- `data:` の URL（`image://data:image/png;base64,...`）は通信しないので、許すかどうかを 02 の工程で決める（6章の Q-3）。
- 出力の SVG も、基準プラグインと同じく DOMPurify（SVG のプロファイル）で無害化する。`data:` 以外の URL を持つ `<image>` と `<a>` も取り除く（二重の守り）。

## 5. SVG の文字列の作り方で分かったこと（段階B で確かめること）

| # | 分かったこと | 段階B で確かめること |
| --- | --- | --- |
| S-1 | `echarts.init(null, テーマ, { renderer: 'svg', ssr: true, width, height })` は、`ssr: true` なら描画先の要素がなくてもよい（要素の検査を飛ばす）。条件書 A-7 を満たす | 描画先なしで描けること |
| S-2 | 文字の幅は、zrender が画面に出さない Canvas の `measureText` で測る（Canvas が使えないときだけ、英字の幅の表で見積もる）。ブラウザでは実際のフォントで測るので、日本語なども正しく測れるはず | B-3。測るときのフォントと、SVG を表示するときのフォント（`font-family`）が同じになること。ECharts の既定のフォントは `sans-serif` |
| S-3 | `renderToSVGString()` は、内部で CSS のアニメーションと強調表示（マウスを載せたとき）の CSS を有効にして文字列を作る。**SVG の中に `<style>` が入ることがある**。`animation: false` でアニメーションの CSS は消えるはずだが、強調表示の CSS（`.zr0-cls-1:hover { ... }` の形）は残る | B-9。`<style>` が入るか。DOMPurify で残すか消すか。Joplin のビューアの `style-src`（インラインのスタイル。未確認）で効くか。消す場合、内部の API（`getZr().painter.renderToString({ cssEmphasis: false, cssAnimation: false })`）を使うかは避けたい |
| S-4 | SVG の中の ID とクラス名（グラデーション、切り抜き、影、模様、CSS のクラス）は、`zr{インスタンスの番号}-` で始まる。番号はページの中で増え続けるので、同じページの図どうしで重ならないはず | B-4。複数の図をページに並べて、グラデーションや切り抜きが隣の図と混ざらないこと。キャッシュした SVG を再び挿入したときも重ならないこと |
| S-5 | SSR の場合、データの点の要素に `ecmeta_*` という属性（系列とデータの番号）が付く | DOMPurify で消えてよいか（静的な図では使わない） |
| S-6 | 圧縮版の配布ファイルは、開発用の検査（`renderToSVGString` を Canvas の描画で呼んだときの例外など）を省いている | 誤った使い方をしても例外にならないことがあるので、試作は圧縮していない版でも動かして確かめる |
| S-7 | ES モジュールで読んだ ECharts は、グローバル変数を作らない。SSR では DOM に何も足さない（測るための Canvas はページに追加しない） | 条件書 A-8。描画の前後で、ページの要素と `<style>` の数が変わらないこと |

### 10.2 見た目（B-3、B-8）

- 日本語などの文字の幅は、zrender が画面に出さない Canvas で測っている（5章の S-2）。ブラウザの実際のフォントで測るので、全角と半角の混在でも凡例の項目やラベルの間隔が正しかった。
- 重なりが検出されたのは、`axisLabel.interval: 0`（すべてのラベルを表示）を指定し、長いラベルを隣に並べた場合だけだった。英字でも同じことが起きる、ECharts の配置の仕様で、文字幅の測り方の問題ではない。
- テーマリバーでは、下の軸のラベルが SVG の下端に1〜2px はみ出していると検出されたが、見た目には問題がない。
- 既定のテーマを暗いページに描くと、題名と軸の文字が背景に埋もれた。基準プラグインと同じく、図の明暗とページの明暗が違うときに背景を敷く（教訓 1.7節）か、既定のテーマでは `backgroundColor` を明るい色にする必要がある。どちらにするかは 02 の工程で決める。

### 10.3 外部通信（B-2）

| 入力 | 何もしない場合 | 入力の検査と出力の検査を通した場合 |
| --- | --- | --- |
| シンボル `image://http://...` | SVG に `<image href="http://...">` が出力され、挿入したときに読まれた（CSP の違反） | 0件 |
| `graphic` の `type: 'image'` | 同上 | 0件 |
| 凡例の `icon: 'image://...'` | 同上 | 0件 |
| 背景の画像のパターン `{ image, repeat }` | **SVG を作る途中で、エンジンが読もうとした**（挿入する前に CSP の違反が出た） | 0件 |
| `title.link` | SVG には何も出ない | − |
| `image://data:image/gif;base64,...` | 通信はない。`<image href="data:...">` として表示される | 入力の検査で取り除いた（Q-3 を「許さない」とした場合） |

- **DOMPurify の SVG のプロファイルは、`<image href="http://...">` を残す**。無害化だけでは外部の画像を止められない。試作では、DOMPurify のフック（`uponSanitizeAttribute`）で、`data:image/` 以外の `<image>` の `href` と、`<a>` の `href` を取り除き、これが効くことを確かめた。
- テスト用のページへのルートの記録（`context.route`）には、どの入力でも何も記録されなかった。外部への要求は、ネットワークより先に CSP が止めるためで、教訓 1.10節のとおり。CSP の違反の記録が必要。
- 画像のパターンの URL は、SVG を作る途中で読まれるので、**出力の検査だけでは止まらない**。入力の検査（4.1節の規則）が必須。

### 10.9 ほかのエンジンにも当てはまること

> **訂正（2026-11-24）**: この節の CSP は、ノートビューアではなく、リッチテキストエディタ（TinyMCE）の CSP だった。作者の Vega-Lite のプラグインの試作の段階C の診断と、Joplin のソースで分かった。ノートビューアには CSP がない。Markdown-it のコンテンツスクリプト（本プラグインの描画の場所）は主ウィンドウの CSP の下で動き、`eval`、`new Function`、WebAssembly は使えないが、外部への `fetch` と画像は止まらない。下の「外部への `fetch` なども `default-src 'self'` で止まる」は、コンテンツスクリプトとノートビューアには当てはまらない。外部の画像はプラグインが止めるという結論は変わらない。正しい記述は設計書の 4.1節（0.7）。記録として、以下は当時のまま残す。

```text
default-src 'self' ; img-src 'self' blob: data: * ; media-src 'self' blob: data: * ;
child-src https://*.youtube.com https://*.youtube-nocookie.com ; object-src 'none' ;
form-action 'none' ; style-src 'self' 'unsafe-inline' * data:
```

- **`img-src` と `style-src` に `*` があり、外部の画像とスタイルシートは CSP では止まらない**。プラグインの入力の検査と、DOMPurify のフック（外部の URL の `<image href>` を取り除く）が、外部の画像を止める唯一の守りになる。段階B のテスト用のページは `img-src 'self' data:` だったので、CSP が先に止めていた。本番のテストでは、CSP に頼らず、ルートの記録と入力・出力の検査で確かめる必要がある。
- `script-src` の指定はなく、`default-src 'self'` が当てはまる。`eval`、`new Function`、WebAssembly は使えない。外部への `fetch` なども `default-src 'self'` で止まる。
- `style-src` に `'unsafe-inline'` があり、SVG の `style` 属性と `<style>` 要素は効く（11.1節）。
- ページは `about:`、プラグインのファイルは `file:` の URL で読み込まれる（基準プラグインのときと同じ）。
- 基準プラグインの記録（Joplin 3.7.22）には `script-src 'self' joplin-plugin://* joplin-content://*` とあり、書き方が違う。Joplin の版で CSP が変わる可能性があるので、本番のプラグインでも、問題の報告を受けたときに CSP を確かめられるようにしておく（基準プラグインの教訓 1.16節）。
- 診断パネルの「追加されたグローバル変数」には、Joplin 本体の Mermaid のもの（`mermaid`、`mermaidInit`、`mermaidReady`、`__esbuild_esm_mermaid_nm`）が出ることがあった。試作のプラグインがエンジンを読んだ後に、Joplin が Mermaid を読み込んだためで、ECharts のものではない（段階B ではグローバル変数を1つも作らなかった。暗いテーマでの確認では `none`）。

### 13.4 印刷で図が出ない原因（Joplin の問題）

Joplin のソース（2026-11-22 の版）の `packages/app-desktop/gui/WindowCommandsAndDialogs/utils/usePrintToCallback.ts` で確かめた。PDF のエクスポートと印刷は、どちらも `InteropServiceHelper` を通って同じ関数（`exportNoteTo_`）で HTML を作るが、呼び出し側が渡す引数が違う。

- PDF のエクスポート（`exportNoteToPdf`）: `plugins: props.plugins` を渡す。プラグインの Markdown-it のコンテンツスクリプトが動く。
- 印刷（`printNote`）: `plugins` を渡さない。プラグインの Markdown-it のコンテンツスクリプトは動かない。

Mermaid が印刷できるのは、Joplin 本体に組み込まれた描画だから。描画の方式に関係なく、**プラグインでは直せない**。回避の方法は、PDF にエクスポートしてから印刷すること。Joplin の修正は、印刷の呼び出しに `plugins: props.plugins` を1行加えるだけで済む見込み。作者は、Joplin に issue も PR も出さず、README で回避の方法を案内すると決めた（設計書 D-13。2026-11-23）。

### 14.1 3回目の試作の作り

- **エンジン**: npm の `echarts` 6.1.0 の `dist/echarts.min.js`（公式の UMD の圧縮版）を、バイト単位でそのまま `contentScript/engine/` にコピーし、Markdown-it のコンテンツスクリプトが実行時に `__non_webpack_require__(__dirname + '/engine/echarts.min.js')` で読む。webpack が `__dirname` を書き換えないよう、`plugin.config.json` の `webpackOverrides` に `node: { __dirname: false }` を書いた。
- **ロケール**: `i18n/langXX-obj.js`（UMD の形のロケールのオブジェクト）を同じく `require` で読み、`registerLocale` する。設計書 0.4 に書いた `lib/i18n/langXX.js` は ES モジュール（`export default`）なので `require` で読めず、`i18n/langXX.js`（UMD）は `require('echarts/lib/echarts')` で本体を読みにいくので、圧縮版だけを同梱する形では使えない（Node で事前に確かめた）。
- **設定**: 公開の設定（図の幅。既定 800）と、隠し設定2つ（Joplin の表示言語、ノートの本文の文字サイズ）。隠し設定は、メインスクリプトが起動時に Joplin の設定を読んで写す。Markdown-it のコンテンツスクリプトは、描画のたびに `options.settingValue(key)` で読む。
- **図の幅**: 設定の幅か、ブロックの `width=` で描き、SVG に `viewBox` を付けて、CSS で `width: 100%; max-width: {描いた幅}px; height: auto` にした（設計書 8.7節、D-12）。
- **背景**: 図の有効テーマとページの明暗（`appearance`）が違うときは、`backgroundColor` で SVG の中に背景を塗る（Light の図は `#ffffff`、Dark の図は `#181818`。設計書 8.5節）。
- ビューアスクリプト（`viewer.js`）は削除した。

### 14.3 PDF の文字が二重になる原因（V-11）

**縁取り（`stroke`）のある文字が原因と確かめた。** ECharts は、ラベルの縁取りを SVG の `<text stroke="..." stroke-width="2" paint-order="stroke">` で書く。Chromium は、これを PDF にするとき、縁取りの文字と塗りの文字の2つを書き込む。

- 8番（`textBorderWidth: 0` を指定）の SVG にも、9番（既定）と同じく `stroke-width="2"` が残っていた。**`textBorderWidth: 0` は効かない。** zrender（ECharts の描画の部分）の `graphic/Text.js` が、縁取りの幅を `style.lineWidth || defaultLineWidth` で決めるので、0 は「指定なし」と同じ扱いになり、既定の 2 に戻る。
- Node で確かめると、`textBorderColor: 'transparent'`（または `'none'`）を指定すれば、縁取りのない `<text>` になった（zrender の `getStroke` が、`transparent` と `none` を縁取りなしとして扱う）。
- 縁取りのない文字（題名、軸の目盛り、凡例）は、どの道具でも正常だった。

二重の文字の出方は、PDF を読む道具によって違った。

| 道具 | 8番の「120」 | 9番の「120」 | 円グラフの「北京市」 | 円グラフの「서울특별시」 |
| --- | --- | --- | --- | --- |
| Adobe Acrobat（コピー） | `120120` | `120120` | − | − |
| Vivaldi（コピー） | `120` | `120` | `北北京京市市` | `서울특별시` |
| `pdftotext`（Poppler） | `112200` | `112200` | `北北京京市市` | `서울특별시` |

Vivaldi は、重なった同じ文字を1つにまとめることがあるが、まとめられるかどうかは文字によって違う。2回目の記録（13.5節）の「112020」も、道具による出方の違いと考えられる。

**対応**: 段階1 で、ラベルの縁取りを `textBorderColor: 'transparent'` で外す処理を入れる（利用者が `textBorderColor` を書いた場合は、利用者の指定を優先する）。常に外すか、エクスポートのときだけ外すかは、見た目を比べて決める（設計書 V-11）。

### 14.4 暗いテーマの補助線が見えない

| | 背景 | 補助線（`splitLine`）の色 |
| --- | --- | --- |
| ECharts の `dark` テーマのまま | `rgb(4,8,16)`（ほぼ黒） | `rgb(40,44,52)` |
| 試作（テーマを指定しない図） | 透明（Joplin の暗いテーマの背景が透ける） | 同じ |
| 試作（`theme=dark` の図。ページが明るいとき、PDF） | `#181818` | 同じ |

ECharts の `dark` テーマの補助線は、ほぼ黒の背景に合わせたとても暗い色で、Joplin の暗い背景や `#181818` の上では明るさの差がほとんどない。軸の線と文字（`rgb(203,203,206)` など）は読める。

**対応**: Dark の図では、補助線の色をプラグインで明るい色に上書きする（`dark` テーマをもとにした独自のテーマを登録する方法を考えている）。利用者が `splitLine` の色を書いた場合は、利用者の指定を優先する。色は、試作か段階2 で候補を並べ、作者が見比べて決める（設計書 V-02）。

### 14.5 力学モデルのグラフが小さい原因（V-12）

ECharts の仕様と確かめた。力学モデルの辺の長さの既定値は `force.edgeLength: 30`（`chart/graph/GraphSeries.js`）で、図の大きさに関係なく、ノートビューアでも PDF でも同じく小さく描かれる。6番（既定）はノードが約 50px の範囲に固まり、7番（`edgeLength: 120`）は約3倍の大きさになった。

**対応**: プラグインでは変えない（利用者の `option` の意味を変えないため）。README に「力学モデルのグラフが小さいときは `force.edgeLength` と `force.repulsion` を大きくする」と書く。

### 14.6 そのほかに分かったこと

- **`options.globalSettings`**: Joplin が Markdown-it のプラグインに渡す options に、`globalSettings` があった（ノートビューアとリッチテキストエディタ。エクスポートのときにもあった）。ここから Joplin の表示言語と本文の文字サイズを読めれば、隠し設定に写す仕組みは要らない。試作の隠し設定は起動時にしか写さないので、Joplin の本文の文字サイズを変えても、再起動するまで図に反映されない。段階1 で中身を確かめる（設計書 V-15）。
- options には、ほかに `contentMaxWidth`、`baseFontFamily`、`scrollbarSize`、`platformName` などもあった（ノートビューア）。
- **HTML のエクスポートの中の SVG**: `viewBox` 属性が `viewbox`（小文字）になっていた。Joplin が書き出すときに小文字にしたとみられる。ブラウザは HTML の中の SVG のこの属性を `viewBox` に直して読むので、表示には影響しない。
- **HTML のエクスポートの大きさ**: ファイル1つの形で約 2.9MB。ほとんどは Joplin 本体の Mermaid のスクリプト（約 2.7MB）で、ECharts の図そのものは小さい。

### 14.7 ほかのエンジンにも当てはまること

開発の指示文書の共通の規則（作者に報告する事項）として、次を報告する。

- **Markdown-it のコンテンツスクリプトから、同梱したファイルを Node の `require` で読める**（デスクトップ版）。webpack の `node.__dirname` を `false` にして実際の場所を得て、`__non_webpack_require__` で読む。エンジンを圧縮し直さずに同梱でき、読み込みは1回あたり 50〜100ms だった。
- **`options.settingValue(key)` で、隠し設定も含めて設定値を読め、設定を変えると Joplin がノートを描き直す**。描き直しの仕組みをプラグインで作る必要はない。
- 縁取りのある SVG の文字は、PDF で二重の文字になる。ラベルに縁取りを使うエンジンは、エクスポートの確認で、文字のコピーを Adobe Acrobat などで確かめる（Chromium の PDF ビューアでは二重が隠れることがある）。
- ライブラリの暗いテーマの色は、ライブラリの既定の背景に合わせてある。背景を透明にしたり、別の色を塗ったりするときは、補助線のような細くて暗い要素が見えるかを確かめる。
