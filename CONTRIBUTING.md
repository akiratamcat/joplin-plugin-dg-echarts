# Contributing to dg-echarts

日本語：[このページの後半](#日本語)（[CONTRIBUTING.ja.md](CONTRIBUTING.ja.md) と同じ内容）

Thank you for your interest. Bug reports, ideas, translations and pull requests are welcome.

## Before you start

- For bugs and requests, please open an [issue](https://github.com/akiratamcat/joplin-plugin-dg-echarts/issues) first.
- For security problems, do not open a public issue. See [SECURITY.md](SECURITY.md).
- The design is described in [docs/design.ja.md](docs/design.ja.md) (in Japanese). The documents in `docs/` are written only in Japanese (`*.ja.md`):
  - `design.ja.md`: the design document (requirements, architecture, tests, release).
  - `lessons-learned.ja.md`: things found in investigations and tests that changed the design or the code (ECharts quirks, Joplin's behaviour).
  - `spike-results.ja.md`: the results of the experiments made before the design (how ECharts runs inside Joplin).
  - `owner-decisions.ja.md`: decisions made by the maintainer.

## Development environment

- Node.js 22 or later and npm (the CI uses Node.js 22)
- Google Chrome (used by the rendering tests; no browser download is needed)
- Joplin desktop 3.1 or later, to try the plugin

```sh
npm ci
npm run dist        # builds publish/io.github.akiratamcat.dg-echarts.jpl
```

Install the `.jpl` with "Install from file" on Joplin's plugin screen (Tools → Options → Plugins; on macOS, Joplin → Settings → Plugins), then restart Joplin.

## How it works

Charts are drawn while Joplin turns Markdown into HTML: the Markdown-it content script loads the bundled ECharts build with Node's `require`, draws each `echarts` block as an SVG string, sanitises it and puts it straight into the HTML. So charts need no script in the page, and they also show in PDF and HTML exports. The viewer script only adds the toolbar. See `docs/design.ja.md`, chapters 5 and 7.

| `tests/` | Unit tests; `tests/render/` rendering tests; `tests/manual/` manual test procedures and records (`*.ja.md`, in Japanese) and test notes to paste into Joplin (`*.md`, in English); `tests/evidence/` files saved during the manual tests |

## Branches and pull requests

The project uses GitHub Flow.

- `main` is the only long-lived branch and is always ready for a release. Releases are tags `vX.Y.Z` on `main`.
- Create a branch from `main` with a prefix: `feature/…` (new or changed features), `fix/…` (bug fixes) or `docs/…` (documents only).
- Open a pull request to `main`. It can be merged when the CI passes (lint, type check, and the tests on Windows, macOS and Linux). The maintainer's own changes go through pull requests too.
- Pull requests are merged with a merge commit (no squash or rebase merge), so each piece of work stays visible in the history.
- Merged branches are deleted (GitHub does it automatically). Their commits stay in `main`.
- Fixes for a released version are made on a `fix/…` branch from `main` and released as a new PATCH version. Older versions get no fixes.
- `spike/…` branches are throw-away experiments: they are not merged and not pushed.

## Rules

- **No network access.** The plugin must not make network requests (see the README). Do not add code or dependencies that do. The static check (`tests/network.test.ts`) fails on new network code, and the rendering tests fail on any request.
- **The input guard** (`src/contentScript/inputGuard.ts`) removes options that load images or take HTML. It is a deny list: when ECharts gets new options of that kind, add them there.
- **The ECharts engine** in `vendor/echarts/` is kept unchanged (the official minified build). It is updated only for security fixes or needed bug fixes. The update steps are in `vendor/echarts/SOURCE.md`.
- **Never run the chart source as JavaScript.** Charts are JSON or YAML data only.
- **Dependencies** are pinned to exact versions. A package that ends up in the plugin needs a license from the allowlist in `scripts/check-licenses.mjs`, and an entry in `scripts/notices.mjs`, `src/thirdParty.ts` and the README tables.
- **Documents**: the files at the top of the repository have an English and a Japanese version (`*.ja.md`); please update both, or say in the pull request which one needs a translation. GitHub and the Joplin plugin site show only the English file, so `README.md`, `CONTRIBUTING.md`, `SECURITY.md` and `CHANGELOG.md` hold the English text and, after it, a copy of the `*.ja.md` file: edit the `*.ja.md` file and run `npm run docs`, never the Japanese half of the English file itself.
- **Changelog**: write each change in both `CHANGELOG.md` and `CHANGELOG.ja.md`. The release notes on GitHub are made from both (English first, then Japanese).

## Translations

Translations are gettext PO files in `locales/` (`ja.po`, `de.po`...), so they can be edited with Poedit or any text editor. The current translations were made with generative AI, so corrections by native speakers are very welcome.

- To correct a translation, edit the `msgstr` in `locales/<locale>.po` and run `npm run i18n:check`.
- Keep placeholders such as `{line}` and `{message}` as they are. ECharts option names (`series`, `xAxis`...), `theme=dark`, `width=` and ```` ```echarts ```` are not translated. Notes for translators are the `#.` comments.
- After changing texts in the source code, run `npm run i18n:extract` to update `locales/echarts.pot` and all PO files.
- A new language needs an entry in `scripts/i18n-common.mjs` and in `src/i18n/gettext.ts` (plural rules). The month names of date axes come from the ECharts locale files in `vendor/echarts/`.

Untranslated texts are shown in English.

## Generative AI

This project is developed with extensive use of generative AI (Anthropic's Claude), and the maintainer reviews every change.
Generative AI is not needed to work on it: the documents and the commands above are all you need.
You may use generative AI for your contribution, but please:

- review and test the result yourself before you submit it, and
- say in the pull request that you used generative AI, and for what.

### ブランチとプルリクエスト

GitHub Flow を使います。

- 長く続くブランチは `main` だけで、いつでもリリースできる状態にします。リリースは `main` のタグ `vX.Y.Z` です。
- `main` から、接頭辞を付けたブランチを作ります：`feature/…`（機能の追加や変更）、`fix/…`（不具合の修正）、`docs/…`（文書だけ）。
- `main` へのプルリクエストを作ります。CI（lint、型チェック、Windows・macOS・Linux でのテスト）が通ればマージできます。作者自身の変更もプルリクエストを通します。
- プルリクエストはマージコミットでマージします（squash や rebase のマージはしません）。作業ごとのまとまりが履歴に残るようにするためです。
- マージしたブランチは削除します（GitHub が自動で削除します）。コミットは `main` に残ります。
- リリースした版の修正は、`main` から作った `fix/…` のブランチで行い、新しい PATCH の版としてリリースします。古い版は修正しません。
- `spike/…` のブランチは、使い捨ての試作です。マージも push もしません。

### 決まり

- **ネットワーク通信をしない。** プラグインはネットワーク通信をしてはいけません（README を参照）。通信するコードや依存パッケージを加えないでください。静的検査（`tests/network.test.ts`）は新しい通信のコードで失敗し、描画テストはどんな通信でも失敗します。
- **入力の検査**（`src/contentScript/inputGuard.ts`）は、画像を読み込む設定や HTML を受け取る設定を取り除きます。禁止リストの方式なので、ECharts にそのような設定が増えたら、ここに加えてください。
- **ECharts のエンジン**（`vendor/echarts/`）は、手を加えずに使います（公式の圧縮版）。更新はセキュリティの修正か、必要な不具合の修正のときだけです。更新の手順は `vendor/echarts/SOURCE.md` にあります。
- **グラフのソースを JavaScript として実行しない。** グラフは JSON か YAML のデータだけです。
- **依存パッケージ**は、版をきっちり固定します。プラグインに入るパッケージは、`scripts/check-licenses.mjs` の許可リストにあるライセンスで、`scripts/notices.mjs`、`src/thirdParty.ts`、README の表にも載せる必要があります。
- **文書**：リポジトリの最上位のファイルには、英語版と日本語版（`*.ja.md`）があります。両方を更新するか、どちらの翻訳が要るかをプルリクエストに書いてください。GitHub と Joplin のプラグインのサイトは英語版のファイルだけを表示するので、`README.md`、`CONTRIBUTING.md`、`SECURITY.md`、`CHANGELOG.md` には、英語の文章と、その後に `*.ja.md` の写しがあります。`*.ja.md` を直して `npm run docs` を実行してください。英語版のファイルの日本語の部分を直接直さないでください。
- **変更履歴**：変更は `CHANGELOG.md` と `CHANGELOG.ja.md` の両方に書きます。GitHub のリリースノートは、両方から作ります（英語の後に日本語）。

### 翻訳

翻訳は `locales/` の gettext の PO ファイル（`ja.po`、`de.po` など）なので、Poedit やテキストエディタで直せます。今の翻訳は生成 AI で作ったので、その言語を話す方の訂正をとても歓迎します。

- 訳を直すときは、`locales/<ロケール>.po` の `msgstr` を直し、`npm run i18n:check` を実行します。
- `{line}`、`{message}` などの置き換えの名前は、そのまま残します。ECharts の設定の名前（`series`、`xAxis` など）、`theme=dark`、`width=`、```` ```echarts ```` は訳しません。翻訳者向けの説明は `#.` のコメントです。
- ソースコードの文字を変えたら、`npm run i18n:extract` を実行して、`locales/echarts.pot` とすべての PO ファイルを更新します。
- 新しい言語には、`scripts/i18n-common.mjs` と `src/i18n/gettext.ts`（複数形の規則）への追加が要ります。日付の軸の月の名前は、`vendor/echarts/` の ECharts のロケールのファイルから来ます。

訳していない文字は英語で表示します。
